# 진입 화면·로그인·직접/SU-Wings 회원가입

`LoginPage`는 `LoginScreen`을 조합한다. `App`의 Query Provider 안에서 `AuthBootstrap`이
초기 refresh와 토큰 구독, 인증된 사용자의 `/me` 조회를 담당한다. 공개 페이지는 초기화 중에도 열린다.

`LandingPage`의 `EntryLayout`이 실제 첫화면을 한 번 렌더링하며 `/login`과 `/signup`은 그 위의
Outlet에 표시된다. 앱 최초 `/`에서 0.8초 대기 후 2초 인트로를 재생한다. 멋사 로고는 재시작하며,
로그인 진입은 즉시 인트로를 완료한다. 직접 로그인/가입 URL과 앱 내 왕복에서는 인트로를 반복하지 않는다.
사이트 공통 폭은 최대 480px이며 로그인/가입 카드는 393px 화면에서 약 336px, 넓은 화면에서 최대 400px다.

로그인 모달은 X·Escape·바깥 포인터 누름/해제로 닫으며, 내부에서 시작한 드래그는 닫지 않는다.
현재 앱이 첫화면에서 연 기록만 뒤로 복귀에 사용하고 직접 진입·새로고침에서는 `/`로 replace한다.
모달은 초기 포커스와 Tab 순환, 배경 inert, 닫은 뒤 진입 버튼 포커스 복귀를 제공한다.
닫기 전환 중 진행 중 로그인은 즉시 취소하며, 상위 안내/복구 다이얼로그의 Escape는 로그인으로 전파하지 않는다.

## 공개 API

다른 페이지/feature에서는 `@/features/auth`에서만 가져온다.

| export                      | 사용 방법                                                                                                                                                 |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `useAuthSession()`          | `status`, `isAuthenticated`, `isInitializing`. 상태는 `initializing`, `authenticated`, `anonymous`, `unavailable`이다.                                    |
| `useMe()`                   | Query의 `data`, `isPending`, `isError`, `error`, `refetch` 등을 사용한다. 로그인하지 않은 동안 요청하지 않으며, 사용자 정보는 이 캐시 한 곳에만 보관한다. |
| `useLogin()`                | 폼 전용. `submit`, `isPending`, `error`, `resetError`. 페이지에서는 준비된 `LoginScreen` 사용을 권장한다.                                                 |
| `useLoginWelcome(enabled?)` | 현재 세션의 명시적 로그인 의도와 성공한 `useMe()` 캐시가 준비되면 `invitation`을 반환한다. `dismiss(sessionVersion)`은 일치하는 의도만 소비한다.          |
| `useLogout()`               | `mutate`/`mutateAsync`, `isPending`, `error`. 204 확인 후 인증을 정리하며, 호출 화면이 이동 목적지를 정한다.                                              |

사용자 데이터가 들어 있는 다른 feature의 query에는 `meta: { authScoped: true }`를 붙인다.
로그아웃, 계정 전환, 최종 401에서 해당 요청을 취소하고 캐시를 제거한다. 찜 여부처럼 로그인에
따라 내용이 바뀌는 공개 API도 이 기준에 포함한다. 각 feature의 별도 store 정리는 해당 담당자가 연결한다.
`studentFeePaid`와 `schoolVerified`는 서로 다른 값이므로 내비게이션 색과 학생 인증 권한을 구분한다.

## 인증 동작

- Access Token은 기존 메모리 저장소만 사용한다. Refresh 쿠키는 브라우저가 관리한다.
- login/refresh는 Bearer 없이 쿠키를 전송하며 JSON의 비어 있지 않은 토큰을 검증한다.
- 보호 요청의 `X-Access-Token`은 같은 세션에서만 반영한다. 토큰 회전으로 `/me`를 제거하지 않는다.
- 로그아웃/계정 전환마다 세션 버전을 바꿔 이전 응답의 토큰 헤더와 401을 무시한다.
- refresh 401은 비로그인, 네트워크/서버/잘못된 응답은 인증 확인 불가로 구분한다. 진행 중 refresh는 공유한다.
- 현재 프로젝트의 최종 401 정리 정책을 유지한다. 보호 API에 대한 자동 refresh/재전송과 갱신 타이머는 추가하지 않았다.
- 비밀번호는 폼과 진행 중 요청에만 존재한다. Query mutation 변수, 전역 store, Storage, URL, 로그에 보관하지 않는다.
- 로그인 입력은 원문을 유지한다. UX상 빈 아이디/비밀번호를 막고 최대 100/128자를 검사하며 이메일·학번·회원가입 복잡도 규칙은 적용하지 않는다.
- 실패 시 입력을 유지하고, 복구는 `ACCOUNT_REACTIVATION_REQUIRED` 응답 뒤 사용자가 동의할 때만 요청한다. 취소나 다음 일반 제출에는 동의를 승계하지 않는다.
- 로그인 성공과 `/me` 조회는 분리한다. 로그인 후 기본 목적지는 기존 `/home`이고 history를 교체한다. `/me`의 500은 인증을 해제하지 않는다.

## 로그인 환영 초대장

`useLogin`은 성공 응답의 취소 신호·세션 버전을 마지막으로 확인한 뒤 `startSession`을 호출하고
새 버전의 초대 의도를 메모리에만 예약한다. 사용자가 동의한 계정 재활성화도 같은 경계를 따른다.
자동 refresh, 초기화, 직접 홈 진입, history state, DEV 미리보기는 의도를 만들지 않는다.
새 세션 시작·로그아웃·최종 보호 요청 401·같은 세션의 확정 비밀번호 재설정은 의도를 지운다.
같은 세션의 응답 헤더 토큰 회전은 예약된 의도와 프로필 캐시를 유지한다. 같은 토큰 문자열로
다시 로그인해도 세션 버전이 달라져 별도의 초대장이 준비된다.

`useMe()`는 기존 Query 결과 형태를 유지한다. 내부에서 query key의 세션 버전을 프로필과
함께 읽으며 `authKeys.me(sessionVersion)` 한 곳에만 보관한다. `useLoginWelcome`도 이 캐시를 공유한다.
현재 버전의 성공한 프로필 전에는 초대장을 렌더링하지 않는다. 조회 지연·오류에는 기존 홈
로딩·재시도 화면을 유지하며, 같은 세션에서 재시도하면 보류된 의도를 사용할 수 있다.
납부자 초대는 `studentFeePaid === true`일 때만 사용하며 `schoolVerified`와 무관하다.
앞뒤 공백을 제거한 이름을 두 곳에 실제 DOM 텍스트로 표시하고, 비어 있으면 `회원님`을 사용한다.

홈은 공개 hook만 사용한다. 초대장은 현재 홈 위의 native modal dialog이며 배경에 `inert`와
5px 블러를 적용한다. 초기 포커스는 제목, Tab은 입장 버튼 안에 머문다. 입장 버튼과 Escape는
현재 의도만 소비하고 홈 제목으로 포커스를 돌린다. 이동·새로고침·프로필 재조회는 하지 않는다.
StrictMode의 effect 정리는 dialog 표시만 닫으며 의도를 소비하지 않는다. 전체 새로고침은
메모리 의도를 버리므로 쿠키로 세션을 복원해도 초대장을 다시 표시하지 않는다.

정확한 Figma 편지지·로고·별 자산은 `../home/assets`에 있으며 투명 실루엣에만 drop-shadow를
적용한다. 작은 화면과 긴 이름은 편지 영역과 세로 스크롤을 늘려 본문·버튼을 유지한다.

## 디자인과 범위

원본은 [로그인 전체 화면 470:1736](https://www.figma.com/design/omsaW8MC3h1oR8gOaq97Ps/2026?node-id=470-1736)과
[로그인 카드 470:1855](https://www.figma.com/design/omsaW8MC3h1oR8gOaq97Ps/2026?node-id=470-1855)다.
Figma는 조회만 했으며 수정하지 않았다. 카드 크기 336×591, 입력 높이 50, 버튼 높이 50,
393×852에서의 카드 위치와 여백을 맞췄다. 기기 상태바는 웹 UI에서 제외한다.

`assets/`의 로고와 아이콘은 Figma 원본 바이트다. 배경도 원본 장식 레이어를 조합한다.
입력/버튼/텍스트는 실제 HTML이며 화면 전체를 이미지로 렌더링하지 않는다.
`LoginConstellations`의 좌표는 원본 470:1750, 470:1763, 470:1780에서 가져왔다.
기존 로그인 자산과 생성 스키마·의존성을 유지한다. 이번 진입 화면 작업은 공통 최대 폭을 480px로 확장한다.

초기화와 오류 안내는 카드 아래 공통 메시지 영역에 표시한다. 오류는 왼쪽 경고 아이콘,
확인 성공은 아이콘 없는 텍스트로 구분하며 필드와 접근성 설명을 연결한다.
복구창은 native dialog에 초기 포커스, Tab 순환,
Escape 취소, 닫은 뒤 포커스 복귀를 적용했다.

아이디 찾기와 비밀번호 재설정은 로그인 카드에서 열리는 실제 계정 복구 흐름이다.
도우미는 클릭 시 준비 중 안내를 표시한다.
직접 입력하기는 `/signup`의 직접 가입으로 연결한다.
홈/마이페이지 구현과 로그아웃 버튼 배치는 각 페이지 담당 범위로 남긴다.

## 로그인 전 계정 복구

아이디 찾기는 이메일·숫자 6자리 인증번호를 확인한 후 서버가 반환한 아이디만 표시한다.
이 API는 이름을 반환하지 않으므로 결과 제목은 `회원님의 아이디는`을 사용한다.
비밀번호 재설정의 `다음으로`는 아이디·이메일·코드의 로컬 형식만 검사한다. 최종
`/api/auth/email/reset-password/verify`가 인증번호 확인과 비밀번호 변경을 한 번에 처리한다.
별도 인증 확인 요청, resetToken, 자동 재전송 또는 자동 로그인은 없다.

모든 복구 요청은 `authMode: none`, 쿠키, 취소 신호를 사용한다. 아이디는 로그인과 같이 원문과
최대 100자를 유지하며 가입의 4–50자 제한을 적용하지 않는다. 새 비밀번호는 가입과 동일한
8–20자 ASCII 출력 문자·대소문자·숫자·특수문자 규칙이며 trim하지 않는다. 복구 코드의
ASCII 숫자 6자리 규칙은 백엔드 계정 복구 가이드에 근거하며 가입의 4–12자 규칙과 별개다.

발송은 계정 존재 여부와 무관한 같은 안내를 표시한다. 성공 시 60초, 발송 제한은 서버의 남은
초를 사용하며 같은 이메일의 대소문자·목적·아이디 변경으로 대기를 우회하지 못한다.
시간당 한도와 인증 시도 제한은 따로 안내하고 재시도 시간 없는 429에 임의의 60초를 적용하지 않는다.

비밀번호 변경의 200 응답이 유효할 때만 요청 당시와 같은 세션의 토큰·사용자 캐시를 정리하고
완료 카드를 유지한다. 네트워크·서버 오류나 잘못된 최종 응답은 변경 결과가 불확실하므로
완료로 표시하거나 자동 반복하지 않는다. 새 비밀번호로 로그인하거나 명시적으로 처음부터
다시 시작하도록 안내한다. 변경 요청 취소는 서버에서 이미 처리한 변경을 되돌리지 않는다.

`RecoveryController`는 로그인 화면 수명 안에만 입력·결과·대기 상태를 둔다. 코드·새 비밀번호·
반환 아이디를 Query mutation cache, Storage, URL, 로그에 쓰지 않는다. 입력 수정·재발송·닫기는
진행 요청과 이전 응답을 무효화하며 세션 버전도 비교한다. 복구를 여는 즉시 진행 중 로그인을
취소한다. 닫기/Escape/로그인 버튼은 원래 로그인 카드와 복구 진입 버튼으로 포커스를 돌린다.

로컬 `tests/auth-preview.mjs`의 `/__recovery-fixture`는 합성 응답·지연·오류를 설정하고
요청 횟수·목적·Bearer 유무·완료 상태만 기록한다. `POST {}`로 초기화한다. 실제 이메일/계정
요청 없이 검증하며 상세 재현 방법과 독립 QA 범위는 해당 AgentFlow 실행의 개발·QA 기록을 따른다.

## 직접 회원가입

`/signup`에서 이름·10자리 숫자 학번·학과를 직접 입력하고 학번 자동 중복 확인을 거쳐 계정·이메일 인증·선택 정보·약관
단계를 진행한다. 일반 학과/학부 27개와 `기타(직접입력)`만 표시한다. 일반 항목은 표시 문자열 그대로,
기타는 직접 입력한 문자열의 앞뒤 공백만 제거해 `department`로 전송한다. 학교 프로필의 학과는 이 목록과 독립적이다.

직접 이름/학번/학과와 확인 결과는 메모리에만 둔다. 학교 모드와 서로 다른 초안 키를 사용하며,
기존 허용 필드인 아이디·이메일·선택 정보만 복원한다. 학번 수정 시 확인 요청을 취소하고 기존 결과를 무효화한다.
`MANUAL` 가입 성공은 자동 로그인이나 학생 인증 성공으로 처리하지 않는다. 통상 진입/취소에서는 학교 API를 호출하지 않는다.
학교 화면에서 명시적으로 직접 가입으로 전환할 때만 임시 학교 프로필을 삭제하고, 실패 시 재시도 안내를 표시한다.

## SU-Wings 회원가입

`SignupPage`와 `SchoolSsoCallbackPage`는 auth feature의 화면만 조합한다. 학교 인증은 현재 창을
`/api/auth/school/authorize`로 이동해 시작하며 학교의 로그인·동의 화면을 사용한다.
`/temporary-auth`에서는 콜백 결과를 해석한 후 주소에서 제거한다. `/signup?source=school`은
서버 프로필 조회와 학번 중복 확인을 통과해야 계정 정보 → 선택 정보 → 약관으로 진행한다.
가입 완료는 자동 로그인 없이 로그인 화면의 완료 안내로 연결한다.

공통 `SignupController`가 계정·이메일·선택 정보·약관과 요청 취소를 관리하고, `SchoolSignupController`는
학교 프로필 조회·만료·삭제를, `ManualSignupController`는 직접 학적 입력·확인을 담당한다. React hook이
이 상태를 구독하며 두 모드는 같은 `SignupSharedSteps` 화면을 사용한다. 모든 가입 API는 쿠키를 전송하며
Bearer 토큰을 사용하지 않는다. 아이디와 비밀번호의
원문을 유지하고, 이메일을 변경하면 기존 인증을 무효화한다. 중복 클릭과 이전 입력에 대한 늦은
응답을 차단하며, 불확실한 최종 가입 응답은 자동 재전송하지 않는다.

아이디·이메일·선택 정보만 `sessionStorage`에 저장한다. 비밀번호·인증번호·학교 정보·인증 완료·동의는
복원하지 않는다. 성공·명시적 취소 시 초안을 지우며, 취소는 서버의 임시 학교 프로필도 삭제한다.
선택 정보는 모두 생략할 수 있고 약관은 사용자가 지정한 운영 페이지를 새 탭에서 연다.

학교 프로필과 가입 화면은 Figma `490:579`, `490:1242`, `490:1409`, `490:1775`의 구성과 기존
로그인 자산을 재사용한다. 계정·선택 정보의 자동 확인과 카드 아래 메시지는 직접 가입과 공유한다.
Figma는 조회만 했다. [운영 적용과 통합 검증 안내](../../../docs/school-signup-release.md)를 참고한다.

## 자동 확인과 화면 피드백

학번은 10자리 숫자, 아이디는 기존 4–50자 규칙, 전화번호는 공백·하이픈 제거 후 10–11자리 규칙을
만족한 뒤 500ms 동안 입력이 멈추면 확인한다. 입력 수정·조합 입력 시 해당 확인 결과를 무효화하고,
이전 단계 이동·취소를 포함한 흐름 변경 시 대기 중 검사와 진행 중 요청을 취소한다.
이전 단계로 돌아가도 변경하지 않은 값의 완료된 확인은 유지한다. 늦은 응답은 현재 입력을 승인하지 못한다.
일시적 실패는 카드 아래에서 다시 확인할 수 있으며, 실패한 요청을 자동으로 반복하지 않는다.

이메일 발송·재전송은 인증번호 입력칸 안의 버튼으로 실행한다. 현재 API 스키마가 인증번호의 고정
길이를 명시하지 않아, 기존 4–12자 입력 범위에서 입력칸을 벗어나거나 Enter를 누르면 자동 확인한다.
예제의 `123456`을 실제 서버의 6자리 제한으로 해석하지 않는다. 이메일 변경과 재전송은 이전 인증을
무효화하며, 성공 후 인증번호를 메모리에서 지운다. 비밀번호는 기존 규칙을 그대로 사용한다.

오류는 빨간 입력 강조와 카드 아래 경고 메시지, 확인 성공은 초록 입력 강조와 아이콘 없는 메시지로
표시한다. 첫 직접 입력 화면부터 네 단계의 진행 표시가 나타난다. 이전 버튼과 비활성 다음 버튼은
GRAY 02, 활성 다음 버튼은 BLUE이며 문구를 버튼 중앙에 배치한다. 선택 정보는 모두 생략할 수 있다.
전화번호를 입력한 경우 현재 값의 중복 확인까지 완료해야 다음으로 진행한다.

최신 디자인 출처·실행 결과·제약은 [로그인·회원가입 Wiki](../../../wiki/auth-login-signup.md)에 기록한다.

## 검증

현재 진입 화면·직접 가입 구현의 결과와 운영 인수 항목은 [통합 검증 기록](../../../docs/entry-signup-verification.md)에 정리한다.
아래 기존 로그인/학교 가입 검증의 횟수와 운영 확인은 당시 이력이며, 이번 실행 결과를 대신하지 않는다.

```sh
npm test
npm run format:check
npm run lint
npm run build
```

회귀 검사는 실제 API에 요청하지 않고 Axios adapter로 정상/실패/취소/지연 응답을 재현한다.
브라우저 검증 서버도 실제 API로 연결하지 않는다.

```sh
node tests/auth-preview.mjs
# http://127.0.0.1:5173/login
```

검증용 아이디는 `invalid`, `recover`, `conflict`, `slow`, `missing`, `server`, `me-fail`이다.
비밀번호는 임의의 비어 있지 않은 테스트 문자열을 사용한다. 그 외 아이디는 정상 로그인 fixture다.
`POST /__auth-fixture`에 `{}`를 보내면 상태와 요청 기록을 초기화한다. `refreshStatus`/`meStatus`로
실패 상태를 선택할 수 있고 `profileName`, `studentFeePaid`, `omitStudentFeePaid`, `meDelayMs`로
현재 프로필의 이름·납부 플래그·지연을 설정한다. `preserveSession: true`는 실패 후 재시도에,
`preserveRequests: true`는 요청 기록 비교에 사용한다. 지연 응답은 시작 시점의 상태를 보존한다.
`GET /__auth-fixture`는 비밀번호·토큰·이름·프로필 원문 없이 요청 종류·Bearer 유무·완료 상태만 반환한다.
이 서버는 localhost 전용 수동 QA 도구다. 실제 연동은 기존 `npm run dev`를 사용한다.

브라우저에서 빈 입력, 실패 후 입력 유지, 중복 클릭, 복구 동의/취소/충돌, 성공 후 이동,
쿠키를 통한 새로고침 복구, 초기화 실패/재시도, 320px와 393px 및 낮은 화면 높이를 확인했다.
기존 인증 회귀 검사 33개와 학교 회원가입 검사 46개를 실행한다. 사용자 승인 후 실제 서버도 조회했으며,
기본 개발 주소 `http://localhost:5173`에서는 쿠키 없는 refresh가 401로 완료되고 로그인 폼이 표시됐다.
임시 포트 5174는 서버에서 `403 Invalid CORS request`로 거절하므로 기본 개발 주소를 사용한다.
기존 실제 축제 계정 로그인 후 메인 이동은 사용자가 확인했다. 새 SU-Wings 가입의 실제 계정 검증은
운영 프런트 반영 후 진행해야 한다. 배포 쿠키 속성·보호 API 401의 서버 갱신 책임도 운영에서 확인한다.

과거 진입 화면 작업에서는 미추적 입력 파일 `.api.json`의 포맷 때문에 전체
`npm run format:check`가 실패해 변경 파일만 별도로 검사했다. 이 문단은 당시 이력이며,
2026-09-23 디자인 일치 작업의 전체 검사 결과는 위 Wiki의 최신 검증 기록을 따른다.
